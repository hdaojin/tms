# accounts APP 总览

## 1. 适用对象

本手册适用于负责后台用户、用户组和权限授权的管理员。

典型角色包括：

- 超级管理员
- 负责给用户组分配业务权限包的系统管理员
- 需要为单个用户追加特殊权限的授权管理员

## 2. 页面入口

后台入口位于 Django Admin：

- `/admin/auth/group/`：维护用户组、组说明、业务权限包、额外原生权限与技术领域范围
- `/admin/auth/user/`：维护用户基本信息、所属用户组、业务权限包与额外原生权限

前台个人入口位于侧边栏“账户 -> 个人账户”：

- “用户中心”：进入系统功能卡片首页。
- “个人资料”：查看和维护当前账号资料。
- “Samba 账户”：查看 Samba 账户开通与改密信息。

前台管理入口位于侧边栏“账户 -> 系统管理”：

- “用户列表”：查看系统内全部用户的姓名、角色、性别、联系方式、宿舍、入读日期、离开日期、激活状态，并可进入用户详情。
- “角色列表”：查看角色名称、英文标识、描述、用户数和已分配的业务权限包，并在页面下方查阅完整的业务权限包参考表。
- “生成邀请码”：超级管理员生成新用户注册邀请码。
- “管理后台”：工作人员进入 Django Admin。

用户列表和角色列表需要“查看全部用户资料”权限。
“用户列表”默认先按账号是否有效排序，有效账号在前、无效账号在后；同一状态内按入读日期倒序排列，没有入读日期的账号排在有入读日期的账号之后；最后用账号主键倒序兜底，保证顺序稳定。

推荐操作顺序：

1. 创建或打开代表业务角色的用户组。
2. 为用户组选择业务权限包，必要时追加额外原生权限。
3. 为需要领域范围的用户组配置一个或多个“技术领域范围”。
4. 将用户加入相应用户组。
5. 只有不依赖技术领域范围的个别场景，才在“用户”里直接补充权限。

## 3. 授权方式

后台授权现在分成两层：

### 3.1 业务权限包

作用：

- 用业务语言授权，而不是手工逐个勾选底层 Django 权限。
- 勾选后系统会自动补齐该业务能力所需的底层权限。

当前已提供的典型业务权限包包括：

- 管理本人资料
- 查看全部用户资料
- 查看通知、发布通知
- 查看、上传或删除会议记录
- 查看训练，以及维护训练计划或训练任务
- 提交、查看全部、管理全部、统计或导出训练日志
- 奖惩对象、录入、审核或查看全部奖惩记录
- 查看标准体系、维护长期技能或维护当前技能树，以及查看或维护评测、评分和考点证据
- 查看、翻译或管理世赛论坛
- 学习、贡献或管理专业词库
- 查看笔记
- 管理本人 Samba 账户
- 查看本人或全部评分结果

例如：

- 勾选“查看全部用户资料”后，系统会自动授予用户列表、用户详情页和角色列表所需的底层权限。
- 勾选“发布通知”后，系统会自动授予通知发布所需的底层权限。
- 勾选“录入奖惩记录”后，系统会自动补齐奖惩记录新增、记录列表查看、奖惩汇总查看等底层权限，减少漏配。
- 勾选“上传会议记录”后，系统会自动授予会议记录上传所需的底层权限。
- 勾选“删除会议记录”后，系统会自动授予会议记录删除所需的底层权限。
- 勾选“录入竞赛总成绩”后，系统会自动授予竞赛总成绩录入所需的底层权限。

### 3.2 额外原生权限

作用：

- 处理业务权限包之外的特殊授权。
- 只在确有需要时使用。

使用建议：

- 常规授权优先使用业务权限包。
- 只有需要临时、细粒度、非模板化授权时，再勾选额外原生权限。
- 不要直接维护 Django 原生 `permissions` / `user_permissions` 投影；系统会在保存授权和部署对账时重算它们。

权限包的定义来自随代码部署的 `core/config/permission_bundles.yml`。后台管理员只能分配权限包，不能在线改变权限包包含哪些底层权限；如需调整定义，应由受信任的维护者修改 YAML、通过部署检查并执行授权对账。

### 3.3 技术领域范围

技术领域范围只在“用户组”页面配置，不在“用户”页面配置。标准技能、当前技能树节点、单领域评测模块和单领域训练任务等领域能力，必须由同一个用户组同时提供：

- 对应业务权限包或额外原生 Django Permission；
- 目标 TechnicalDomain 的技术领域范围。

例如，A 组拥有“修改 Skill + Linux 范围”，B 组只有“查看 Skill + Windows 范围”，同时属于两组的用户可以修改 Linux、查看 Windows，但不能修改 Windows。直接给用户本人追加 `change_skill` 也不能绕过此限制。

## 4. 常见任务

### 4.1 给一个用户组配置“录入奖惩记录”能力

步骤：

1. 进入“用户组”列表。
2. 打开目标用户组。
3. 在“业务权限包”里勾选“录入奖惩记录”。
4. 保存。

结果：

- 该组会自动获得录入奖惩记录所需的底层权限。
- 后续新加入该组的用户会继承这组权限。

### 4.2 给单个用户追加特殊权限

步骤：

1. 进入“用户”列表。
2. 打开目标用户。
3. 先确认其所属用户组是否已经覆盖主要权限。
4. 如仍需不依赖技术领域范围的特殊授权，再在“额外原生权限”里补充。
5. 保存。

结果：

- 用户会保留组继承权限。
- 额外原生权限只对该用户本人生效。
- 需要技术领域范围的写权限仍必须通过用户组配置，用户直授不能绕过。

### 4.3 查看用户与角色

步骤：

1. 打开侧边栏“账户 -> 系统管理”。
2. 进入“用户列表”，查看全部用户及其所属角色；无角色用户会显示“未分配”。
3. 进入“角色列表”，查看每个角色的英文标识、描述、用户数和业务权限包。
4. 在角色列表下方的“业务权限包参考”表中，查阅权限包的配置编码、用途说明和自动附加的底层 Django 权限。

说明：

- “角色”包含 Django 用户组，以及账号的“工作人员”“超级用户”系统身份；超级用户不重复显示工作人员身份，不同角色会用 soft 风格的彩色标签区分，用户列表和用户详情保持一致。
- “英文标识”和“描述”来自用户组扩展信息。
- “业务权限包”显示管理员在后台为该角色配置的业务化授权名称。
- “业务权限包参考”按照部署配置中的声明顺序完整展示，不分页；它是只读参考，不能在该页面修改权限包定义。
- “激活”显示账号是否有效；绿色圆形勾表示有效账号，红色圆形叉表示无效账号。
- 用户列表中只有“姓名”“角色”“性别”“出生日期”“入读日期”“离开日期”“激活”列可点按排序。
- 如果管理员将已有账号从有效改为无效，且该用户资料没有填写“离开日期”，系统会自动把失效当天写入“离开日期”；已填写的离开日期不会被覆盖。

### 4.4 设置新注册用户的默认用户组

1. 在 Django Admin 打开唯一的“站点配置”。
2. 选择“新用户默认用户组”，或留空表示注册后不自动加入任何组。
3. 保存后，新完成注册的用户会加入该组；账号是否激活仍按原有审核流程处理。

## 5. 使用提醒

1. 用户组授权优先于单用户散权，便于后续维护。
2. “业务权限包”是推荐入口，“额外原生权限”是高级兜底入口。
3. 如果一个业务能力已经有权限包，不建议再手工逐条勾选同一批底层权限。
4. 组里的业务权限包与用户自己的业务权限包会分别生效，互不覆盖。
5. 技术领域能力必须由同一个用户组同时提供 Permission 与 Scope，不能把不同用户组的两部分拼接使用。

## 6. 常见问题

### 6.1 为什么我已经勾选了业务权限包，还会看到“额外原生权限”区域？

因为特殊场景仍可能需要单项授权。该区域保存的是独立的显式授权意图，不是系统根据权限包展开后的原生权限列表。

### 6.2 应该优先给组授权还是给用户授权？

优先给组授权。只有当某个用户需要个别例外权限时，才建议直接给用户追加额外原生权限。

### 6.3 业务权限包会不会覆盖我手工加的权限？

不会。业务权限包和额外原生权限分别保存；最终有效权限是两者的并集。即使某项额外权限也包含在权限包中，移除权限包后，该显式权限仍会保留，直到管理员明确取消。
