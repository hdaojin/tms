# accounts APP 总览

## 1. 适用对象

本手册适用于负责后台用户、用户组和权限授权的管理员。

典型角色包括：

- 超级管理员
- 负责给用户组分配业务权限包的系统管理员
- 需要为单个用户追加特殊权限的授权管理员

## 2. 页面入口

后台入口位于 Django Admin：

- `/admin/auth/group/`：维护用户组、组说明、业务权限包、额外原生权限与技术领域范围
- `/admin/auth/user/`：维护用户基本信息、所属用户组、业务权限包与额外原生权限

前台个人入口位于侧边栏“账户 -> 用户中心”：

- “功能面板”：进入系统功能卡片首页，URL 保持不变。
- “个人资料”：所有已登录的有效账号均可查看和维护本人未锁定资料，无需角色或额外权限；锁定后只读，由管理员解锁。
  姓名按“姓 + 名”显示；邮箱可在锁定前填写、修改或清空，保存并锁定后也不可修改。
- “Samba 账户”：查看 Samba 账户开通与改密信息。

前台管理入口位于侧边栏“账户 -> 系统管理”：

- “用户列表”：查看系统内全部用户的姓名、角色、性别、联系方式、宿舍、入读日期、离开日期、激活状态，并可进入用户详情。
- “角色列表”：查看角色名称、英文标识、描述、用户数和已分配的业务权限包，并在页面下方查阅完整的业务权限包参考表。
- “生成邀请码”：超级管理员生成新用户注册邀请码。
- “管理后台”：工作人员进入 Django Admin。

用户列表需要“查看全部用户资料”权限；角色只读列表需要原生“查看组”权限。角色创建、编辑、复制、成员与领域分配及他人权限诊断，仅超级管理员可以操作。
“用户列表”默认先按账号是否有效排序，有效账号在前、无效账号在后；同一状态内按入读日期倒序排列，没有入读日期的账号排在有入读日期的账号之后；最后用账号主键倒序兜底，保证顺序稳定。

推荐操作顺序：

1. 创建或打开代表业务角色的用户组。
2. 为用户组选择业务权限包，必要时追加额外原生权限。
3. 为需要领域范围的用户组配置一个或多个“技术领域范围”。
4. 将用户加入相应用户组。
5. 只有不依赖技术领域范围的个别场景，才在“用户”里直接补充权限。

## 3. 授权方式

角色前端和后台都复用同一套授权配置与权限投影服务，授权分成两层：

### 3.1 业务权限包

作用：

- 用业务语言授权，而不是手工逐个勾选底层 Django 权限。
- 勾选后系统会自动补齐该业务能力所需的底层权限。

当前已提供的典型业务权限包包括：

- 管理本人资料
- 查看全部用户资料
- 查看通知、发布通知
- 查看、上传或删除会议记录
- 查看训练，以及维护训练计划或训练任务
- 提交、查看全部、管理全部、统计或导出训练日志
- 奖惩对象、录入、审核或查看全部奖惩记录
- 查看标准体系、维护长期技能或维护当前技能树，以及查看或维护评测、评分和考点证据
- 查看、翻译或管理世赛论坛
- 学习、贡献或管理专业词库
- 查看笔记
- 管理本人 Samba 账户
- 查看本人或全部评分结果

例如：

- 勾选“查看全部用户资料”后，系统会自动授予用户列表、用户详情页和角色列表所需的底层权限。
- 勾选“发布通知”后，系统会自动授予通知发布所需的底层权限。
- 勾选“录入奖惩记录”后，系统会自动补齐奖惩记录新增、记录列表查看、奖惩汇总查看等底层权限，减少漏配。
- 勾选“上传会议记录”后，系统会自动授予会议记录上传所需的底层权限。
- 勾选“删除会议记录”后，系统会自动授予会议记录删除所需的底层权限。
- 勾选“录入竞赛总成绩”后，系统会自动授予竞赛总成绩录入所需的底层权限。

### 3.2 额外原生权限

作用：

- 处理业务权限包之外的特殊授权。
- 只在确有需要时使用。

使用建议：

- 常规授权优先使用业务权限包。
- 只有需要临时、细粒度、非模板化授权时，再勾选额外原生权限。
- 不要直接维护 Django 原生 `permissions` / `user_permissions` 投影；系统会在保存授权和部署对账时重算它们。

权限包的定义来自随代码部署的 `core/config/permission_bundles.yml`。后台管理员只能分配权限包，不能在线改变权限包包含哪些底层权限；如需调整定义，应由受信任的维护者修改 YAML、通过部署检查并执行授权对账。

### 3.3 技术领域范围

技术领域范围只在“用户组”页面配置，不在“用户”页面配置。标准技能、当前技能树节点、单领域评测模块和单领域训练任务等领域能力，必须由同一个用户组同时提供：

- 对应业务权限包或额外原生 Django Permission；
- 目标 TechnicalDomain 的技术领域范围。

例如，A 组拥有“修改 Skill + Linux 范围”，B 组只有“查看 Skill + Windows 范围”，同时属于两组的用户可以修改 Linux、查看 Windows，但不能修改 Windows。直接给用户本人追加 `change_skill` 也不能绕过此限制。

## 4. 常见任务

### 4.1 给一个用户组配置“录入奖惩记录”能力

步骤：

1. 进入“用户组”列表。
2. 打开目标用户组。
3. 在“业务权限包”里勾选“录入奖惩记录”。
4. 保存。

结果：

- 该组会自动获得录入奖惩记录所需的底层权限。
- 后续新加入该组的用户会继承这组权限。

### 4.2 给单个用户追加特殊权限

步骤：

1. 进入“用户”列表。
2. 打开目标用户。
3. 先确认其所属用户组是否已经覆盖主要权限。
4. 如仍需不依赖技术领域范围的特殊授权，再在“额外原生权限”里补充。
5. 保存。

结果：

- 用户会保留组继承权限。
- 额外原生权限只对该用户本人生效。
- 需要技术领域范围的写权限仍必须通过用户组配置，用户直授不能绕过。

### 4.3 查看用户与角色

步骤：

1. 打开侧边栏“账户 -> 系统管理”。
2. 进入“用户列表”，查看全部用户及其所属角色；无角色用户会显示“未分配”。
3. 进入“角色列表”，查看每个角色的英文标识、描述、用户数和业务权限包。
4. 在角色列表下方的“业务权限包参考”表中，查阅权限包的配置编码、用途说明和自动附加的底层 Django 权限。

说明：

- “角色”包含 Django 用户组，以及账号的“工作人员”“超级用户”系统身份；超级用户不重复显示工作人员身份，不同角色会用 soft 风格的彩色标签区分，用户列表和用户详情保持一致。
- “英文标识”和“描述”来自用户组扩展信息。
- “业务权限包”显示管理员在后台为该角色配置的业务化授权名称。
- “业务权限包参考”按照部署配置中的声明顺序完整展示，不分页；它是只读参考，不能在该页面修改权限包定义。
- “激活”显示账号是否有效；绿色圆形勾表示有效账号，红色圆形叉表示无效账号。
- 用户列表中只有“姓名”“角色”“性别”“出生日期”“入读日期”“离开日期”“激活”列可点按排序。
- 激活状态与离开日期独立管理：前端和后台启停账号均不会自动填写或清空离开日期，人工修改日期也不会改变激活状态。既有日期保留。

#### 前端用户管理（仅有效超级管理员）

1. 在用户列表按账号、完整姓名或学号搜索，并按激活状态、角色筛选。多个条件取交集，“未分配”表示没有所属用户组。
2. 通过表格行复选框选择用户，或通过表头复选框全选当前页。本页全部选中且还有其他分页时，操作栏才出现“选择全部 N 位匹配用户”，可进一步选中全部分页结果。全匹配模式不能逐人排除，可点“清空选择”后调整筛选。翻页、排序或改变筛选会清空选择。
3. 在表格上方的紧凑操作栏选择激活、取消激活、追加角色、移除角色、填写离开日期或清空离开日期，再点“执行”；默认“请选择操作”，必须先选用户和操作。
4. 追加／移除角色、填写离开日期会先进入参数页，显示已固定的姓名、账号和人数；角色可多选，填写日期使用同一个日期。参数页不会因新增匹配用户而扩大名单；填好后点“预览变更”。其他操作直接进入预览，均尚未保存。
5. 核对固定名单、人数和原值、新值，再确认保存。预览 30 分钟有效，相关状态或权限配置变化后须重新预览；任何无效目标导致整批不保存，无需变更的用户会跳过并统计。
6. 取消或保存后恢复原列表的筛选、排序和页码，并清空勾选；操作导致原页码超出结果范围时回到最后有效页。

追加和移除角色保留其他角色、个人直接授权与账号标志。前端禁止取消激活任何超级管理员，也禁止批量增减超级管理员的角色；选中受保护账号时整批报错，须调整选择。

用户详情的“管理激活状态与离开日期”提供单人启停、填写或清空日期，同样需要预览确认。管理员可维护已锁定资料和超级管理员的离开日期，但不能因此修改其他锁定字段。允许未来日期；离开日期不得早于该用户的入读日期。

#### 在用户详情保存、锁定与解锁资料

仅有效超级管理员可在前端用户详情直接维护全部个人资料字段及邮箱；账号和姓名仍只读，角色、激活状态使用原有独立入口。普通查看者即使拥有模型修改权限，仍只能查看该页面。

- 未锁定时，可在“详细资料”区块底部点击“保存”；点击“锁定资料”并确认，会先校验、保存当前全部表单内容（包括账号信息区的邮箱），再锁定。
- 校验失败时保留输入并显示错误，不保存资料，也不锁定。
- 已锁定时，全部资料和邮箱只读，“保存”禁用。点击“解锁资料”并确认只解除锁定，不保存其他字段；随后管理员及用户本人均可重新编辑。
- 本人资料页的“锁定资料”同样提交并保存当前完整表单，不再由弹窗单独提交空资料。普通用户不能自行解锁。

锁定和解锁均需弹窗确认，普通保存无需额外预览。独立离开日期入口可维护锁定资料日期的既有例外保持不变。

### 4.4 设置新注册用户的默认用户组

1. 在 Django Admin 打开唯一的“站点配置”。
2. 选择“新用户默认用户组”，或留空表示注册后不自动加入任何组。
3. 保存后，新完成注册的用户会加入该组；账号是否激活仍按原有审核流程处理。

### 4.5 初始化与复制默认角色

迁移后显式运行 `uv run manage.py bootstrap_tms --dry-run` 查看预览，再运行 `uv run manage.py bootstrap_tms` 并确认。系统提供“选手、教练、班务”三个默认角色，不自动添加成员或技术领域，也不设置注册默认组。

| 角色 | 默认能力 |
|---|---|
| 共同能力 | 本人资料、查看通知、本人奖惩、提交与回复反馈 |
| 选手 | 本人任务执行与日志、查看标准、按既有范围查看竞赛及本人评分、可作为奖惩对象 |
| 教练 | 本人日志、查看训练和标准、维护本领域技能与当前树、维护授权对象内的任务、竞赛、评分和考点证据 |
| 班务 | 录入与查看全体奖惩、发布通知、上传和查看会议记录 |

在角色列表点击角色名称进入配置，按 APP 搜索权限包，配置技术领域并分配成员，点击“预览变更”核对能力、领域、成员及受影响人数，再保存。预览后修改表单或其他管理员修改授权时，需要重新预览。

竞赛日常维护包不包含“新增竞赛与考核”，由管理员统一创建。此调整也适用于选用该包的自定义角色；现有数据库授权不会自动改写，管理员需预览后保存角色或显式重新投影，额外原生授权仍需单独检查。

默认教练组的领域为空。可以复制为“Linux 教练”“Windows 教练”“Network 教练”，为每个组独立配置领域和成员；也可以让一个人加入多个领域教练组。复制只复制权限组合和说明，成员、领域留空，后续修改互不联动。

范围区别：标准跨领域可读，维护按领域；周期和计划的读取为全系统，任务、评分与证据按各自对象规则收窄。周期、计划、成员统筹以及全体训练日志查看需要另授。跨领域对象可能需要显式教练分配；角色不自动建立周期成员身份、当前周期或任务教练关系。班务目前是全站范围，不提供班级隔离。

笔记、词汇学习、论坛、Samba、删除和导出等能力另行选择。奖惩审核仍在后台，班务默认不包含审核、账号管理或完整用户资料查看。

默认教练使用不含删除能力的当前树与证据日常维护包；移除树节点和移除技能映射分别勾选对应权限包。既有“维护当前技能树”“考点证据维护”组合保留原来的移除能力，管理员应按描述区分。

普通初始化保留现有默认角色的修改；`--force` 在完整预览后恢复声明的名称、说明及权限包，仍保留成员、技术领域和额外原生权限。名称与其他稳定标识冲突时须先人工处理，不会凭名称合并角色。

### 4.6 查看用户有效权限来源

超级管理员可从用户详情进入“查看有效权限及来源”，检查各角色、领域、个人直接权限及合并结果。移出某角色后，其他组和个人授权可能仍提供相同能力。未激活账号会标注为配置状态，不能按有效权限使用。

个人直接授权继续在后台维护；需要领域范围的能力必须在同一角色组内配置。无业务授权的登录账号仍可使用功能面板、本人资料及密码等基础账户功能，明确公开的关于页面和倒计时不受此限制。

### 4.7 从用户侧分配角色

超级管理员可在用户列表或用户详情点击“分配角色”，搜索并勾选多个角色，预览新增、移除角色及原生权限变化后保存。预览后若角色配置、用户授权或表单变化，需要重新预览。移除角色也可能撤销其提供的领域范围，即使相同原生权限仍由其他角色提供。

此操作只修改用户的组成员关系，不修改个人直接授权、角色领域、账号激活状态、超级管理员标志或任何训练业务身份。其他工作人员即使拥有查看用户资料的权限，也不能分配角色。

## 5. 使用提醒

升级前先执行 `uv run manage.py preview_feedback_access`，只读列出激活账号缺少的反馈查看、提交、回复和附件权限。由管理员按需要为现有组补授反馈权限包，不必向不使用反馈的账号开放。修改权限包目录后，先执行 `uv run manage.py reconcile_permission_assignments --dry-run` 核对展开差异，再显式执行 `uv run manage.py reconcile_permission_assignments --apply`。这些命令不会替代账号激活或角色成员分配。

1. 用户组授权优先于单用户散权，便于后续维护。
2. “业务权限包”是推荐入口，“额外原生权限”是高级兜底入口。
3. 如果一个业务能力已经有权限包，不建议再手工逐条勾选同一批底层权限。
4. 组里的业务权限包与用户自己的业务权限包会分别生效，互不覆盖。
5. 技术领域能力必须由同一个用户组同时提供 Permission 与 Scope，不能把不同用户组的两部分拼接使用。

## 6. 常见问题

### 6.1 为什么我已经勾选了业务权限包，还会看到“额外原生权限”区域？

因为特殊场景仍可能需要单项授权。该区域保存的是独立的显式授权意图，不是系统根据权限包展开后的原生权限列表。

### 6.2 应该优先给组授权还是给用户授权？

优先给组授权。只有当某个用户需要个别例外权限时，才建议直接给用户追加额外原生权限。

### 6.3 业务权限包会不会覆盖我手工加的权限？

不会。业务权限包和额外原生权限分别保存；最终有效权限是两者的并集。即使某项额外权限也包含在权限包中，移除权限包后，该显式权限仍会保留，直到管理员明确取消。
