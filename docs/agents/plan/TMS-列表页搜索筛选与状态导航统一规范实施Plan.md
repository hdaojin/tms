# TMS 列表页搜索、筛选与状态导航统一规范实施 Plan

> 状态：待 Codex 执行  
> 基线分支：`develop`  
> 建议执行分支：`feature/list-ui-standardization`（从最新 develop 创建）  
> 项目技术栈：Django 6、Python 3.13、django-htmx、django-tables2、Tailwind CSS 4、DaisyUI 5、Alpine.js CSP build、Iconify  
> 本 Plan 的目标：统一 TMS 全站列表页的搜索、过滤、快捷分类、复杂筛选、列表工具区和后续编码规范，并迁移现有适用列表。

---

## 1. 背景与当前问题

当前 TMS 已具备一定的列表页公共基础设施：

- `core.utils.listing.FilterableListMixin`
- `core.utils.listing.ListFilterSpec`
- `templates/components/list_filter_toolbar.html`
- `templates/common/table_page.html`
- `templates/components/table_wrapper.html`
- `templates/components/list_bulk_actions.html`
- `static/js/list-bulk-actions.js`

现有规范已经规定“搜索筛选区 → 批量操作区 → 结果列表区”，但实际页面仍存在多种入口：

1. 公共列表页使用 `common/table_page.html`。
2. Feedback、论坛、部分 Standards 页面直接 include 公共筛选组件，但外层布局和结果容器 ID 不完全一致。
3. 部分页面使用业务专用 GET 表单，例如训练日志、月度统计、长期赛事人员等。
4. 部分列表把搜索控件放在筛选控件之后，例如论坛主题列表。
5. 部分列表把业务模式切换（例如“已有成员 / 添加成员”）当作普通筛选项，和搜索框混排。
6. 有些新增、导入等业务操作通过覆盖 `content` 区块放置，容易与标题、搜索筛选栏形成不一致的垂直结构。
7. 普通筛选条件增加时，当前工具栏可能持续横向增长，缺少统一的高级筛选策略。
8. 当前没有一个明确、可复用的“状态快捷分类”规范；状态条件容易被实现成普通下拉框，也容易被误做成所有列表都有的装饰性标签。

本次不是简单调整 CSS，而是统一设计、公共组件契约、列表迁移和长期编码规范。

## 2. 已确认的设计决策

以下决策视为已确认，不再在实施过程中重新讨论：

### 2.1 默认布局：搜索在最左，筛选在后，重置靠右

普通列表默认采用单行工具栏：

```text
┌────────────────────────────────────────────────────────────────────┐
│ [ 🔍 搜索关键词________________________ ] [状态 ▼] [类别 ▼] [重置] │
└────────────────────────────────────────────────────────────────────┘
```

规则：

- 搜索框默认是第一个控件，位于最左侧。
- 搜索框桌面端自适应占据剩余空间，具有合理的最小宽度。
- 普通筛选控件紧随搜索框排列，顺序由业务配置明确决定。
- 重置操作位于最右侧，不与新增、导出等业务动作混淆。
- 业务确有强优先级条件时允许例外，但必须说明原因；不得仅因为 Python 中先声明了某个字段，就把它排在搜索框之前。
- 不得把排序控件默认混入筛选区。优先使用 django-tables2 列排序；只有业务有明确需要时才提供独立排序控件。

### 2.2 扩展布局一：状态快捷分类

仅适用于存在少量、高频、语义明确状态分类的列表，例如工作任务、训练任务、意见反馈、通知等。

```text
┌────────────────────────────────────────────────────────────────────┐
│ 全部 128 | 待处理 12 | 处理中 35 | 已完成 76 | 已逾期 5           │
├────────────────────────────────────────────────────────────────────┤
│ [ 🔍 搜索关键词________________________ ] [负责人 ▼] [重置]       │
└────────────────────────────────────────────────────────────────────┘
```

规则：

- 状态快捷分类是独立的分类导航，不等同于普通筛选下拉框。
- 放在搜索筛选栏上方；页面没有快捷分类时完全省略，不留空白。
- 每个选项应明确表达当前筛选范围，当前项有清晰选中态。
- 数量仅在后端能以正确权限范围和相同筛选口径可靠计算时显示；不得为了显示数字制造昂贵查询。
- 点击分类应保留其他合法搜索/筛选条件，清除冲突的状态参数，并重置无效分页参数。
- 分类切换、浏览器前进/后退、刷新和复制 URL 必须保持一致。
- 不得将“模式切换”伪装成状态分类。诸如“已有成员 / 添加成员”属于业务模式导航，应放在页面上下文工具区或明确的模式切换位置。
- 不得为了统一而给所有列表增加状态分类。

### 2.3 扩展布局二：高级筛选

当筛选项较多（通常超过 3 个普通筛选项），或包含日期区间、多选、低频业务条件时，采用“基础搜索 + 高级筛选”：

```text
┌────────────────────────────────────────────────────────────────────┐
│ [ 🔍 搜索关键词____________________________ ] [高级筛选 3 ▼]      │
├────────────────────────────────────────────────────────────────────┤
│ 筛选条件（展开）                                                   │
│ [条件1 ▼]       [条件2 ▼]       [条件3 ▼]                          │
│ [开始日期]      [结束日期]      [条件6 ▼]                          │
│                                                   [重置] [查询]    │
├────────────────────────────────────────────────────────────────────┤
│ 已选：条件1 ×  条件3 ×  时间范围 ×                                 │
└────────────────────────────────────────────────────────────────────┘
```

规则：

- 高级筛选只承载低频、次要或复杂条件；最常用的 1–2 个过滤条件可以继续放在搜索栏同一行。
- 默认是否展开由页面配置决定；默认收起时仍需显示当前已生效条件摘要/标签，避免用户不知道列表为何被过滤。
- 高级筛选使用明确的“查询”按钮；用户完成多项设置后一次提交，避免每改一个字段都发起请求。
- 重置必须清除搜索、基础筛选、高级筛选和快捷分类条件，并回到默认列表状态。
- 对于当前筛选条件较少的页面，不要为了形式统一强行使用折叠面板。
- 多选控件必须正确处理同名参数、空值、非法值和重置；不得破坏现有业务校验。
- 当前条件标签可逐项移除；移除后更新 URL 和结果。无法安全地逐项移除的专用表单，可先提供整体重置，不要实现不可靠的伪交互。

### 2.4 列表页面整体区域顺序

普通管理列表按以下顺序组织：

1. 页面标题及页面级业务操作（新增、导入等）。
2. 状态快捷分类（可选）。
3. 搜索与筛选工具栏（可选）。
4. 当前生效筛选条件摘要（复杂筛选或确有必要时显示）。
5. 批量操作区（仅有已授权批量动作时显示）。
6. 结果列表、空状态和分页。

业务操作不得伪装成筛选条件；筛选 GET 表单与批量 POST 表单必须分离，禁止嵌套表单。

### 2.5 响应式布局

- 桌面端：搜索框优先占据剩余宽度；常用筛选紧随其后；重置靠右。
- 中等屏幕：控件允许换行，不允许挤压到无法识别或横向溢出。
- 移动端：搜索框独占一行；筛选控件按可用宽度换行；重置保留明确可触达入口。
- 高级筛选展开区采用响应式网格；桌面端每行建议 2–3 个控件。
- 不得依赖固定像素宽度导致页面在常见笔记本分辨率下横向溢出。
- 搜索输入、下拉、日期控件继续使用 DaisyUI 与项目现有表单样式，不引入新的 UI 框架。

## 4. 实施范围与边界

### 4.1 本次必须完成

- 建立清晰、可维护的通用列表工具栏组件契约。
- 默认搜索控件自动位于最左侧；普通筛选项位于其后。
- 重置操作稳定靠右。
- 支持可选状态快捷分类。
- 支持可选高级筛选区域。
- 支持复杂筛选的当前条件摘要/标签；仅对适用页面启用。
- 统一业务操作、快捷分类、搜索筛选、批量操作、结果列表的垂直层级。
- 统一普通列表、卡片列表及自定义列表适用的公共交互。
- 迁移现有适用列表，不能只改公共组件后声称全站完成。
- 修复迁移后暴露的模板、HTMX、URL、分页和筛选保留问题。
- 更新 `docs/developer/ui.md` 和 `AGENTS.md`，使后续 Codex 有唯一明确规范。
- 增加针对公共组件和代表性页面的测试。

### 4.2 本次不做

- 不改变任何业务模型、业务状态、权限定义和统计口径。
- 不改变现有列表的筛选语义、搜索字段、默认排序和分页大小。
- 不把所有页面强制改成 django-tables2；树、矩阵、评分录入等继续按其内容选用结构。
- 不为没有明确业务价值的列表新增状态快捷分类。
- 不为筛选条件很少的列表强行增加高级筛选面板。
- 不把 Django Admin 的 list_filter/search_fields 作为本次前台列表 UI 改造对象。
- 不引入 React、Vue 或其他前端框架。
- 不新增无必要的全局 JavaScript 状态管理。
- 不在本次顺手重构与列表 UI 无关的业务逻辑。

## 5. 设计与组件实现

### Phase 0：最新代码盘点与分类

1. 阅读 `AGENTS.md`、`docs/developer/ui.md` 和相关 ADR。
2. 搜索全仓所有列表视图、列表模板和筛选表单。
3. 建立盘点表，至少包含：
   - APP / 页面 / URL name；
   - 模板与 View；
   - 当前筛选实现（公共 Mixin / 专用 Form / 手写 GET / 无筛选）；
   - 搜索字段；
   - 筛选条件及顺序；
   - 是否适合状态快捷分类；
   - 是否适合高级筛选；
   - 批量操作；
   - HTMX target / partial；
   - 迁移策略。
4. 分类为：
   - A：普通搜索 + 少量筛选；
   - B：状态快捷分类 + 搜索筛选；
   - C：高级筛选；
   - D：业务模式切换或专用筛选；
   - E：树、矩阵、详情内小列表等特殊列表；
   - F：无筛选列表。
5. 将盘点结果写入实施总结或单独的清单文档，确保没有遗漏。

### Phase 1：公共筛选组件和配置契约

优先扩展现有基础设施，不另起一套框架。

重点文件：

- `core/utils/listing.py`
- `templates/components/list_filter_toolbar.html`
- `templates/common/table_page.html`
- 必要时新增少量公共 partial，例如快捷分类栏、筛选条件摘要、高级筛选内容容器。

建议的契约方向：

1. `ListFilterSpec` 明确区分搜索、普通筛选、高级筛选；新增字段必须有合理默认值，兼容既有声明。
2. 搜索字段不论其在旧配置中的声明位置，默认始终在最左侧。若存在多个 search spec，应测试并明确拒绝或定义行为，不可静默渲染多个全文搜索框。
3. 普通筛选的顺序由配置显式决定；高级筛选字段进入高级区域。
4. 支持页面提供快捷分类数据（例如稳定 URL 参数、标签、数量、当前选中态）；不要把快捷分类作为普通 select 处理。
5. 业务模式切换单独建模/渲染，不与状态分类混淆。
6. 所有筛选条件继续使用独立 GET form；批量动作仍使用独立 POST form。
7. 组件输出正确的 `aria-label`、`aria-expanded`、键盘可用控件和语义化结构。
8. 组件不得推测用户权限；业务 View 显式传入已授权的入口和动作。
9. 组件不得自行查询数据库；计数和分类由 View/selector 传入。
10. 保持旧页面调用方式兼容，分阶段迁移，不进行一次性破坏性改造。

推荐的上下文概念（名称可由 Codex 按当前代码风格调整，但语义必须保留）：

- `list_filter_controls`：基础搜索与普通筛选控件。
- `list_filter_advanced_controls`：高级筛选控件。
- `list_filter_tabs`：状态快捷分类。
- `list_filter_active_items`：已应用条件摘要。
- `list_filter_advanced_expanded`：高级筛选默认展开状态。
- `list_filter_submit_mode`：自动筛选或显式提交。

不要为了上述名称机械新增大量 dataclass 或抽象层。若现有 `ListFilterSpec` 能清楚表达，可直接扩展它。

### Phase 2：默认搜索筛选栏视觉与交互

1. 调整 `list_filter_toolbar.html`：
   - search 控件在最左；
   - 普通筛选项依次排列；
   - 重置在最右；
   - 使用合理的 flex/grid 和 min-width；
   - 桌面端搜索自适应；
   - 窄屏下搜索独占一行，筛选换行。
2. 控件标签可以使用可访问性标签；视觉上不必每个控件都占用一行标签。
3. placeholder 必须描述可搜索内容，不使用含糊的“搜索”。
4. 自动筛选仍采用适当 debounce（当前 400ms 可保留）；Enter 立即提交。
5. 搜索清空、下拉切换、日期修改、浏览器前进/后退和 HTMX 替换必须保持正确。
6. 重置链接清空所有列表查询参数，但保留明确需要保留的页面上下文参数（例如 plan tab、cycle id）；通过白名单配置，不允许无条件清空或保留任意 GET 参数。
7. 不允许筛选表单包住批量 POST 表单，也不允许反向嵌套。

### Phase 3：状态快捷分类

只给适用列表启用。候选页面由 Phase 0 盘点决定，重点评估：

- Feedback：状态分类。
- WorldSkills Forum：动态/主题状态或内容类型；只有用户确实常用且语义清晰时才加。
- Training：任务/日志/执行记录；必须遵守当前业务状态定义，不把不同对象的状态混为一谈。
- Notices：若实际有消息状态或通知类别，按真实业务字段决定。
- 其他工作任务列表：若已有独立 APP/列表，按其实际状态模型决定。

实现要求：

- 快捷分类链接使用 GET URL，支持可复制、刷新、浏览器历史。
- 选中态、计数、空状态和分页行为一致。
- 点击分类时保留搜索及不冲突的筛选条件。
- 计数应按用户可见 queryset 计算；无权限对象绝不能进入计数。
- 不能为了快捷分类额外产生每项单独查询；优先使用聚合或已有统计 selector。
- 无法可靠提供计数时允许不显示数量。

### Phase 4：高级筛选

1. 先识别筛选条件较多、低频条件明显或有日期区间/多选条件的页面。
2. 保留最常用搜索和 1–2 个常用筛选在基础行，其余放高级区。
3. 展开/收起不应丢失已填写的值。
4. 显示已生效条件摘要；单项移除应能准确清除 URL 参数并刷新结果。
5. 高级筛选默认采用显式“查询”提交；如果页面现有过滤语义依赖自动刷新，需保留或合理迁移并测试。
6. 查询和重置都必须正确处理分页。
7. 对复杂业务 Form，不要求把 Form 拆成多个 `ListFilterSpec`；可以由业务模板使用公共布局插槽，但必须遵循相同视觉规范和 URL/HTMX 约定。

### Phase 5：全站现有列表迁移

按照 Phase 0 盘点逐项处理，不得只修改公共模板。

至少重点检查：

- Accounts 用户列表；
- Training 训练周期、训练计划、周期成员、计划成员、训练日志、月度统计、计划详情日程/任务、计划参与选手；
- Meetings 会议记录；
- Feedback 意见反馈；
- Standards 技能树版本、技能树节点、技能项目；
- Assessments 竞赛/考核、评测模块、赛事角色、长期赛事人员；
- Evidence 考点证据；
- Scoring 评分方案；
- Behaviors 行为记录；
- Glossary 词条管理；
- WorldSkills Forum 论坛主题和动态信息流；
- Notices、Notes 等实际存在的列表。

迁移要求：

- 普通列表优先使用 `common/table_page.html` + `FilterableListMixin` + 公共工具栏。
- 专用业务表单不适合 Mixin 时，保留其业务校验和查询逻辑，但复用公共视觉布局和结果容器约定。
- 页面级新增/导入/导出操作放在页面标题或列表工具区，不混入筛选表单。
- 状态快捷分类只用于有明确高频状态分类的页面。
- 多条件页面使用高级筛选；少量条件保持单行。
- 业务模式切换独立于搜索和过滤条件。
- 所有 HTMX 请求必须返回正确 partial，target ID 唯一且稳定。
- 搜索/筛选、排序、分页、状态分类切换后不得保留无效页码。
- 所有查询参数均需白名单处理；非法筛选值不得静默扩大结果集。
- 保持权限范围先于搜索/筛选，不能由筛选参数扩大 queryset。

## 6. 重点风险与保护措施

1. **查询语义变化**：迁移只改变 UI 和参数编排，不得改变搜索字段、过滤 lookup、排序和权限范围。
2. **GET 参数丢失**：尤其注意训练计划 tab、cycle、mode、fragment、page、sort 等业务参数；逐项定义白名单。
3. **HTMX partial 错误**：外层容器不能在 innerHTML 替换后重复嵌套；partial 不包含外层 target 容器。
4. **表单嵌套**：搜索 GET 表单与批量 POST 表单必须是兄弟节点。
5. **状态分类口径错误**：计数必须复用与列表一致的权限范围和业务条件。
6. **高级筛选误触发**：多条件提交时不得因为 change/input 自动提交而提前发出不完整查询。
7. **日期条件错误**：日期区间需分别验证格式、起止顺序、时区和空值。
8. **移动端挤压**：不能只在桌面端检查。
9. **不必要的抽象**：公共组件只抽取多个列表真正共享的结构，不建立通用筛选 DSL 或过度复杂的配置系统。
10. **无关改造**：不顺带改表格列、业务状态、权限、批量操作服务和模型。
