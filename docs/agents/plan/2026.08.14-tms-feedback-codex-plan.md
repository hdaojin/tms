# 1. 产品定位

TMS 新增一个轻量的内部“意见反馈”系统，借鉴 GitHub Issues 的核心交互，但只保留 TMS 当前真正需要的能力。

它同时承担四类场景：

1. **Bug**：反馈 TMS 功能错误、异常、不可用或体验问题。
2. **功能需求**：提出希望 TMS 新增或增强的功能。
3. **意见建议**：对 TMS、训练安排或日常管理事务提出改进建议。
4. **投诉**：对训练管理、日常事务、服务或管理问题进行投诉/反映。

核心体验：

```text
用户提交反馈
  ↓
可选择匿名 / 私密
  ↓
可附截图或附件
  ↓
形成 #编号
  ↓
相关人员回复讨论
  ↓
工作人员更新状态
  ↓
填写处理结果
  ↓
已解决 / 已关闭
```

目标是：**简单、易用、可追踪、对匿名和私密内容足够安全。**

# 4. 匿名与私密的语义

必须严格区分两个概念。

## 4.1 匿名 `is_anonymous`

匿名的含义是：

- 数据库仍然保存真实 `author`；
- 普通用户页面不显示作者身份；
- 只有具备 `feedback.view_anonymous_identity` 权限的人员才能查看匿名提交者真实身份；
- 匿名不是“系统无法追踪”。

显示规则：

- 匿名反馈的创建者：显示 **匿名用户**；
- 该创建者在自己匿名反馈下继续回复：显示 **匿名反馈人**；
- 其他用户回复：正常显示用户姓名；
- 管理员不能因为拥有反馈管理权限就自动看到匿名身份，匿名身份权限必须独立。

不要在 HTML 源码、`data-*`、title、图片 alt、附件元信息、API/HTMX fragment 等普通用户可获得的响应中泄漏匿名用户真实姓名或用户 ID。

## 4.2 私密 `is_private`

私密反馈只允许：

1. 反馈创建者本人；
2. 具备 `feedback.view_private_feedback` 权限的人员；
3. superuser。

访问规则必须同时覆盖：

- 反馈详情
- 回复
- 附件图片
- 附件下载
- 搜索结果
- 列表计数
- HTMX fragment

对无权访问的用户优先返回 `404`，避免泄漏私密反馈是否存在。

## 4.3 匿名与私密组合

四种组合均允许：

```text
公开 +实名
公开 +匿名
私密 +实名
私密 +匿名
```

投诉新建时默认：

```text
is_private = True
```

但这是表单交互默认值，不是数据库强制约束；用户仍可选择公开投诉。

# 5. 状态设计

使用 `models.TextChoices`：

```text
OPEN         open          待处理
IN_PROGRESS  in_progress   处理中
RESOLVED     resolved      已解决
CLOSED       closed        已关闭
```

默认：

```text
OPEN
```

V1 不实现复杂状态机；具备反馈管理权限的工作人员可以在四个状态之间切换。

业务规则：

- 状态为 `RESOLVED` 或 `CLOSED` 时，`resolution` 必填；
- 进入 `RESOLVED` / `CLOSED` 时记录 `resolved_by`、`resolved_at`；
- 如果从 `RESOLVED` / `CLOSED` 重新切回 `OPEN` / `IN_PROGRESS`：
  - 清空 `resolved_by`；
  - 清空 `resolved_at`；
  - 保留原 `resolution` 文本供工作人员编辑，不自动删除内容；
- 下一次再次解决/关闭时覆盖 `resolved_by` / `resolved_at`。

页面上的字段名称统一使用 **处理结果**，不要使用“解决方案”，因为投诉和事务意见不一定存在技术“解决方案”。

# 6. 数据模型

建议核心模型只保留 3 个：

```text
Feedback
├── FeedbackReply 0..N
└── FeedbackAttachment 0..N
       └── 可属于 Feedback 本身或某一条 Reply
```

不要为了未来需求新增状态历史、标签、订阅、指派等模型。

## 6.1 枚举

在 `feedback/models.py`：

### `FeedbackCategory`

```text
BUG          bug          Bug
FEATURE      feature      功能需求
SUGGESTION   suggestion   意见建议
COMPLAINT    complaint    投诉
```

### `FeedbackStatus`

按第 5 节定义。

---

## 6.2 `Feedback`

建议字段：

```text
category        CharField(choices=FeedbackCategory, db_index=True)
title           CharField("标题", max_length=200)
content         TextField("详细描述")

author          ForeignKey(settings.AUTH_USER_MODEL, SET_NULL, null=True,
                           related_name="feedbacks_created")
is_anonymous    BooleanField("匿名提交", default=False)
is_private      BooleanField("仅工作人员可见", default=False, db_index=True)

status          CharField(choices=FeedbackStatus, default=OPEN, db_index=True)
resolution      TextField("处理结果", blank=True)
resolved_by     ForeignKey(settings.AUTH_USER_MODEL, SET_NULL, null=True, blank=True,
                           related_name="feedbacks_resolved")
resolved_at     DateTimeField(null=True, blank=True)

created_at      DateTimeField(auto_now_add=True)
updated_at      DateTimeField(auto_now=True, db_index=True)
```

Meta：

```text
ordering = ["-updated_at", "-pk"]
```

至少增加适合列表过滤的索引，避免过度设计：

```text
(category, status)
(is_private, status)
```

如果数据库已经能够从单字段 `db_index` 足够覆盖当前查询，不机械创建重复索引；由 Codex 根据当前数据库/查询计划做最小判断。

自定义权限：

```text
manage_feedback          管理意见反馈
view_private_feedback    查看私密反馈
view_anonymous_identity  查看匿名反馈人身份
```

模型级规则：

- 标题 trim 后不能为空；
- 正文 trim 后不能为空；
- `RESOLVED/CLOSED` 时 `resolution` 必须非空；
- 不在 `save()` 中机械调用 `full_clean()`；按 TMS 当前规范由表单/service 写入边界负责完整校验。

编号：

- 使用 `pk` 直接展示为 `#{{ feedback.pk }}`；
- URL 使用 `/feedback/<int:pk>/`；
- 不增加额外 `number`/UUID 公共编号字段。

## 6.3 `FeedbackReply`

字段：

```text
feedback        ForeignKey(Feedback, CASCADE, related_name="replies")
author          ForeignKey(settings.AUTH_USER_MODEL, SET_NULL, null=True,
                           related_name="feedback_replies")
content         TextField("回复内容")
created_at      DateTimeField(auto_now_add=True)
```

V1 不支持回复编辑，因此不需要 `updated_at`。

规则：

- 回复内容不能为空；
- 只有“当前有权查看该 Feedback 的用户”才能回复；
- 已关闭反馈 V1 仍允许工作人员回复；普通用户对 `CLOSED` 反馈不再显示回复表单；
- 普通用户能否对 `RESOLVED` 继续回复：允许，便于指出问题尚未真正解决；
- 创建回复后更新所属 `Feedback.updated_at`，让列表按最新活动排序。

匿名显示规则不要存到 `FeedbackReply` 字段中，统一由展示 policy 判断：

```text
feedback.is_anonymous == True
AND reply.author_id == feedback.author_id
=> "匿名反馈人"
```

这样避免给每条回复维护重复匿名状态。

## 6.4 `FeedbackAttachment`

统一承载图片和普通文件，不再单独设计 `FeedbackImage`。

字段：

```text
feedback          ForeignKey(Feedback, CASCADE, related_name="attachments")
reply             ForeignKey(FeedbackReply, CASCADE, related_name="attachments",
                             null=True, blank=True)

file              FileField(... PrivateMediaStorage("feedback") ...)
original_filename CharField("原始文件名", max_length=255)
file_size          PositiveBigIntegerField("文件大小")
content_type       CharField("MIME 类型", max_length=255, blank=True)
uploaded_by        ForeignKey(settings.AUTH_USER_MODEL, SET_NULL, null=True,
                             related_name="feedback_attachments_uploaded")
created_at         DateTimeField(auto_now_add=True)
```

语义：

```text
reply is NULL   => 反馈正文附件
reply != NULL   => 某一条回复的附件
```

一致性规则：

- 当 `reply` 非空时，必须保证 `reply.feedback_id == feedback_id`；
- 该跨模型一致性在 `clean()` + service 写入边界验证；
- 不使用 `GenericForeignKey`；
- 不增加“图片/文件 kind”数据库字段，图片类型可根据受控扩展名派生；
- 模板展示图片时仅允许 V1 白名单图片扩展名，不能仅相信浏览器 MIME。

删除文件：

- 复用 `core.utils.signals.register_file_cleanup_signals(...)`；
- 删除 attachment / feedback / reply 后不得留下孤儿文件；
- 对相关删除行为写测试。

# 7. 附件策略

## 7.1 允许格式

在 `core/constants.py` 增加反馈附件专用常量，不复用语义不相干的 Forum/Notice 常量。

V1 建议：

```text
图片：
jpg, jpeg, png, webp

办公文档：
pdf, doc, docx, xls, xlsx, ppt, pptx

文本/技术文件：
txt, md, csv, json, yaml, yml, xml, conf, cfg, ini, log

压缩包：
zip
```

明确不直接允许：

```text
exe, com, msi
bat, cmd, ps1
sh, py, js, php
svg, html, htm
```

如果用户确实需要提交脚本，可打包成 ZIP。

## 7.2 大小与数量

为了 V1 简单，反馈正文和回复使用同一套“每次提交”限制：

```text
单个文件最大：20 MB
单次提交最多：10 个附件
单次附件总大小：50 MB
```

增加常量：

```text
FEEDBACK_ATTACHMENT_UPLOAD_MAX_SIZE_MB = 20
FEEDBACK_ATTACHMENT_MAX_COUNT = 10
FEEDBACK_ATTACHMENT_MAX_TOTAL_SIZE_MB = 50
```

并在 `core/uploads.py` 增加：

```text
FEEDBACK_ATTACHMENT_UPLOAD_SPEC
```

复用现有 `UploadSpec`。

单文件：由 `UploadSpec` 完成扩展名、大小、现有文件签名检查。

多文件：在 `FeedbackForm` / `FeedbackReplyForm` 或共享的轻量 helper 中校验：

- 数量 <= 10；
- 总大小 <= 50 MB；
- 错误信息明确指出限制。

不要为这两个表单新建通用“上传框架”。如果确实有 5~10 行可复用逻辑，可以放 `feedback/forms.py` 的私有 helper。

## 7.3 存储路径

使用：

```python
PrivateMediaStorage("feedback")
```

`upload_to` 使用 UUID 文件名，保留安全扩展名，不使用原始文件名作为磁盘文件名。

建议：

```text
YYYY/MM/DD/<uuid>.<ext>
```

例如：

```text
media-private/feedback/2026/08/14/3cb8....png
```

原始文件名只保存在数据库 `original_filename`。

清理：

- 将 `/`、`\` 等路径分隔符从显示文件名中替换/移除；
- 限制最终显示名称长度；
- 下载响应时使用安全后的原始显示名。

# 8. 附件访问安全

反馈附件不能在模板中直接使用 `attachment.file.url` 作为公共链接。

统一通过受控 Django view：

```text
/feedback/attachments/<int:pk>/
```

流程：

```text
请求 Attachment
  ↓
加载 attachment.feedback
  ↓
执行 Feedback 可见性判断
  ↓
无权：404
有权：FileResponse
```

返回规则：

### 安全图片

允许内嵌：

```text
jpg/jpeg/png/webp
```

用于：

- 缩略图
- DaisyUI Modal / `<dialog>` 大图查看

响应：

- `Content-Disposition: inline`
- 正确、受控的 Content-Type
- `X-Content-Type-Options: nosniff`

### 普通文件

响应：

- `Content-Disposition: attachment`
- 下载名使用安全处理后的 `original_filename`
- `X-Content-Type-Options: nosniff`

不要提供 Office/PDF 在线 iframe 预览器。

不要信任上传请求中的 `UploadedFile.content_type` 作为安全判定依据；它可作为记录信息，但展示/inline 策略由允许扩展名和现有签名校验共同决定。

# 9. 业务权限与可见性

建议新增 `feedback/permissions.py` 或 selector/policy 中的清晰函数，不要把条件散落在多个 view/template。

核心函数至少包括：

```text
can_view_feedback(user, feedback)
can_reply_feedback(user, feedback)
can_manage_feedback(user)
can_view_anonymous_identity(user)
get_feedback_author_label(user, feedback)
get_reply_author_label(user, feedback, reply)
```

## 9.1 普通登录用户

V1 的“提交意见反馈”是 TMS 基础能力，所有已登录用户均可：

- 查看公开反馈；
- 创建反馈；
- 查看自己提交的私密反馈；
- 回复自己可见且未关闭的反馈；
- 查看/下载自己有权访问的附件。

不要求为了这一基础能力给每个现有角色批量写入新的权限数据迁移。

## 9.2 反馈管理员

自定义权限：

```text
feedback.manage_feedback
```

允许：

- 修改反馈状态；
- 填写/修改处理结果；
- 对已关闭反馈继续回复；
- 在管理界面执行必要处理。

注意：`manage_feedback` **不自动意味着**可以查看匿名真实身份。

## 9.3 私密反馈人员

权限：

```text
feedback.view_private_feedback
```

允许查看所有私密反馈及附件。

## 9.4 匿名身份查看人员

权限：

```text
feedback.view_anonymous_identity
```

只有在本身已经有权查看该反馈时，才可以进一步看到匿名用户身份。

即：

```text
view_private_feedback
```

和：

```text
view_anonymous_identity
```

必须保持独立。

## 9.5 Permission Bundle

在 `core/config/permission_bundles.yml` 增加管理用 bundle，bundle code 不要与原生 permission codename 重名。建议：

```text
feedback.handle_feedback
```

名称：`处理意见反馈`，至少包含：

```text
feedback.manage_feedback
feedback.view_private_feedback
```

如当前权限包惯例要求把相关默认 `view_*` 权限一并列出，则按现有风格补充 `Feedback` / `FeedbackReply` / `FeedbackAttachment` 的查看权限；不要为此改变运行时对象范围规则。

匿名身份权限不要默认塞进处理 bundle；如当前权限配置风格允许，再单独建立：

```text
feedback.identify_anonymous
```

其中只包含：

```text
feedback.view_anonymous_identity
```

用于极少数高级管理人员。

不要在 migration 中自动给所有现有 Group 授予“查看匿名身份”。

# 11. Service 设计

该功能涉及多模型 + 私有文件 + 状态变更，因此允许建立精简 `feedback/services.py`。

不要为每个 CRUD 动作都包装 service；只把真正涉及业务不变量/多模型事务的动作放进去。

建议至少：

```text
create_feedback(..., attachments, actor)
add_feedback_reply(feedback, content, attachments, actor)
update_feedback_status(feedback, status, resolution, actor)
```

## 11.1 `create_feedback`

职责：

1. 验证表单已经清洗的数据；
2. 对每个附件再次调用 `FEEDBACK_ATTACHMENT_UPLOAD_SPEC.validate_file()` 作为写入边界校验，不只依赖浏览器和 MIME；
3. `transaction.atomic()`；
4. 创建 `Feedback`；
5. 创建 `FeedbackAttachment`；
6. 对每个文件保存：
   - 安全原始文件名
   - file_size
   - content_type（仅记录，不作为授权依据）
   - uploaded_by
7. 任一数据库步骤失败时不留下部分数据库记录。

注意 Django 文件存储并不与数据库事务天然原子；如文件保存后数据库事务失败，应按项目现有文件处理方式做最小补偿清理，或确保创建流程不会静默留下孤儿文件。不要为此引入复杂事务框架。

## 11.2 `add_feedback_reply`

职责：

1. 再次验证 actor 有权查看/回复；
2. 对附件再次调用 `FEEDBACK_ATTACHMENT_UPLOAD_SPEC.validate_file()`；
3. 在原子数据库事务中创建 Reply；
4. 创建 Reply Attachments；
5. 更新 `Feedback.updated_at` 为当前时间；
6. 返回 reply。

## 11.3 `update_feedback_status`

职责：

1. 检查 `feedback.manage_feedback`；
2. 状态为 `RESOLVED/CLOSED` 时要求处理结果；
3. 设置/清理 `resolved_by`、`resolved_at`；
4. 更新 `updated_at`。

# 13. 前端附件选择器

需要提供一致的附件选择体验，但不要引入第三方上传库。

在现有 `static/js/alpine-components.js` 中增加 CSP build 可用的 Alpine component，例如：

```text
feedbackAttachmentPicker
```

职责：

- 管理本地待上传文件数组；
- 文件选择；
- 拖拽加入；
- 粘贴剪贴板图片；
- 删除某个待上传文件；
- 生成图片 `URL.createObjectURL()` 预览；
- 组件销毁或删除时 `URL.revokeObjectURL()`；
- 同步真实 `<input type="file" multiple>` 的 `FileList`，可使用 `DataTransfer`；
- 前端预检查数量/大小，仅用于即时 UX；
- 服务端仍必须重新完整验证。

CSP 要求：

- 不写原生 inline `<script>`；
- 不写 `onclick=`；
- 不写 `javascript:` URL；
- Alpine 复杂逻辑放 `static/js/alpine-components.js`；
- 模板中的 Alpine 表达式保持 CSP build 可执行的简单形式。

## 13.1 粘贴截图

监听组件区域或表单的 `paste`：

```text
ClipboardEvent.clipboardData.items
```

只接受 `kind=file` 且图片 MIME 的剪贴板项；转成 File 后加入当前附件列表。

为没有文件名的剪贴板截图生成仅用于浏览器提交的名称，例如：

```text
screenshot-20260814-164500.png
```

服务端仍按 UUID 保存。

## 13.2 拖拽

拖放区域提供：

- `dragover` 阻止默认行为；
- drop 读取 `dataTransfer.files`；
- 清晰的 hover 状态；
- 键盘可访问的普通 file input 作为兜底。

# 14. HTMX 使用范围

不要为了“使用 HTMX”而把所有页面强行拆成 fragment。

推荐：

## 14.1 列表筛选

列表筛选表单可以使用 GET + HTMX：

```text
category/status/q/scope
   ↓
更新反馈列表区域
```

同一 URL 同时支持完整页和 fragment；使用 `request.htmx` 判断。

同时保证关闭 JS 后普通 GET 仍然可用。

## 14.2 回复提交

回复表单允许使用 HTMX 提升体验：

- `hx-post`
- `hx-encoding="multipart/form-data"`
- 成功后替换/追加讨论区域或重新渲染回复列表 fragment；
- 清空回复内容和本地附件预览。

如果实现中发现附件选择器与 HTMX swap 生命周期显著增加复杂度，可以 V1 退回标准 POST + redirect，不要为了局部无刷新引入脆弱 JS。

## 14.3 管理状态

状态/处理结果可使用普通 POST 或小型 HTMX fragment，优先选择代码最少、测试最清晰的方案。

权限和业务校验全部在服务端执行，不能依赖 HTMX 按钮隐藏。

# 25. 删除策略

V1 前台不提供：

- 删除 Feedback；
- 删除 Reply；
- 删除已提交 Attachment。

原因：

- 意见、投诉、Bug 处理记录具有留痕价值；
- 避免匿名投诉提交后被任意篡改或删除；
- 简化权限和附件一致性。

Django Admin / superuser 仍可以按 Django 管理能力删除记录；删除时文件清理 signal 必须正常工作。

V1 前台也不提供编辑 Feedback/Reply。

用户补充信息统一通过回复完成。

# 31. 验证命令

# 34. 实现原则总结

本次功能最重要的设计原则：

1. **像 GitHub Issue 一样直观，但不要复制 GitHub Issue 的复杂度。**
2. **匿名是前台身份保护，不是不可追踪。**
3. **私密与匿名必须是两套独立语义和权限。**
4. **截图只是附件的一种展示方式，底层统一为 `FeedbackAttachment`。**
5. **反馈和回复都支持附件。**
6. **附件从第一天开始使用 TMS 现有私有文件体系。**
7. **服务端权限检查是唯一可信边界，前端隐藏按钮不代表授权。**
8. **不做异步临时上传，V1 保持一次表单提交。**
9. **反馈正文/回复 V1 不编辑、不删除，补充信息通过回复追加。**
10. **按最新 AGENTS.md 做最小必要验证，不无条件全量测试。**

# 36. 实现时核对的官方文档

Codex 在遇到框架/API 细节时以**执行当时的官方最新文档**为准；不要因为文档版本比项目声明版本新就自动升级依赖。当前计划重点涉及：

- Django 6：File uploads、Managing files、File storage API、Security / User-uploaded content。
