# TMS「今日训练任务」大屏改版实施 Plan

> **目标分支：** `develop`\
> **实施方式：**
> 在现有公开训练大屏上做定向改版，不重建训练业务、不新增独立 APP。\
> **设计基准：**
> 用户已确认的深蓝科技风效果图（四时段横向卡片、计划轮播、底部统计区）。\
> **重要约束：** 必须遵循仓库 `AGENTS.md`、`CONTEXT.md` 及 ADR
> 0014；开始编码前先重新读取当前分支文件，不能假设本 Plan
> 编写时的代码仍是最新状态。

------------------------------------------------------------------------

## 1. 目标与范围

将 `/training/board/`
从当前纵向任务卡片和溢出分页布局，改造成训练室使用的全屏看板：

1.  深蓝科技风视觉，适合训练室电视或显示器长期展示。
2.  页面主体固定为四个横向时段卡片：早读、上午、下午、晚上。
3.  同一时刻只展示一份训练计划；多份计划通过轮播切换，不把多个计划纵向堆叠。
4.  每个时段展示领域、负责教练和训练任务。
5.  单个时段任务过多时，卡片内部截断并显示"......还有 N
    项任务"，不出现滚动条，也不把任务卡片截成半行。
6.  底部展示计划级训练统计：选手任务执行完成率、今日任务数、训练领域分布、全天时间轴。
7.  当前时段根据服务器时间自动高亮。
8.  保留公开授权、自动刷新、手动切换、暂停轮播和刷新失败处理等已有能力。

本次只改造训练大屏及其直接相关的公开数据查询、测试和说明文档。**不修改训练计划编制、排班、任务发布、选手任务执行等业务流程。**

## 3. 已确认的页面结构

### 3.1 全屏页面

采用独立的看板视觉，不显示常规业务页面的导航、侧栏和页脚。仅对训练大屏本身设置深色主题和样式，不修改全站
DaisyUI 主题。

整体结构：

``` text
┌──────────────────────────────────────────────────────────────┐
│ 今日训练任务                                      日期/星期   │
├──────────────────────────────────────────────────────────────┤
│ 计划名称   值班教练             上一份  1/3  下一份  15s自动切换 │
├──────────────┬──────────────┬──────────────┬──────────────────┤
│    早读      │    上午      │    下午      │       晚上       │
│ 时间         │ 时间         │ 时间         │ 时间             │
│ 专业领域     │ 专业领域     │ 专业领域     │ 专业领域         │
│ 负责教练     │ 负责教练     │ 负责教练     │ 负责教练         │
│              │              │              │                  │
│ 训练任务     │ 训练任务     │ 训练任务     │ 训练任务         │
│ 任务列表     │ 任务列表     │ 任务列表     │ 任务列表         │
│              │              │ ……还有更多   │                  │
├──────────────────────────────────────────────────────────────┤
│ 完成率 │ 今日任务数 │ 训练领域分布 │ 全天时间轴             │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 顶部标题区

-   左侧显示"今日训练任务"。
-   右侧显示服务器业务时区日期，格式如 `2026年11月11日 · 星期三`。
-   标题与日期在 1920×1080 和 1366×768
    下均应保持清晰，不得因固定大字号挤压计划信息栏。

### 3.3 计划信息栏与轮播

-   显示当前计划完整标题、当天值班教练。
-   多个计划时显示上一份、下一份、页码（如 `1 / 3`）、圆点指示和
    `15s 自动切换`。
-   一次只展示一个计划；四个时段卡片始终属于当前计划。
-   只有一份计划时隐藏轮播控制和页码，不留空白占位。
-   计划顺序采用稳定排序（标题、主键等），避免刷新后顺序随机变化。
-   每个计划容器设置稳定的 `data-plan-id`。60
    秒刷新后，如果当前计划仍然存在，尽量保持当前计划；当前计划已被移出大屏或撤回发布时，切换到有效计划。
-   手动切换后重新开始 15 秒计时；暂停后不自动切换。
-   尊重
    `prefers-reduced-motion`，浏览器标签页处于后台时暂停自动轮播，回到前台后恢复。
-   轮播按钮使用语义化
    `button`，提供可访问名称；当前页码和圆点状态应能被辅助技术识别。

### 3.4 四个时段卡片

固定顺序：

1.  早读
2.  上午
3.  下午
4.  晚上

每张卡片包含：

-   时段名称、开始和结束时间。
-   专业领域标签。
-   `负责教练：姓名`。文案保持"负责教练"，不要写成"负责教练人"。
-   训练任务标题列表。
-   当前时段状态（进行中、已结束、未开始），当前时段使用青蓝色边框或柔和高亮。

当前时段判定使用服务器时间及排班时间快照：

-   `starts_at <= now < ends_at`：进行中。
-   `ends_at <= now`：已结束。
-   `starts_at > now`：未开始。
-   时间快照缺失时，不猜测状态。

即使某个时段没有已发布任务，也应保留对应时段卡片，按实际排班类型展示"暂无任务""休息"或"不安排"等状态，不应因为任务数为零而导致四列布局缺失。

### 3.5 多任务省略规则

不使用滚动条，也不无限缩小字号。

建议采用以下实现：

1.  时段卡片有稳定的主体高度；任务列表区域使用 `min-height: 0` 和
    `overflow: hidden`。
2.  单个任务标题最多显示两行，过长标题在自身末尾省略。
3.  多个任务按现有 `order`、主键顺序展示。
4.  根据卡片实际可用高度，只显示能够完整容纳的任务项；不能显示半张任务卡片。
5.  超出部分隐藏，在列表末尾显示醒目的弱强调提示，例如
    `… 还有 4 项任务`。
6.  所有任务都能显示时隐藏该提示。
7.  浏览器尺寸变化、字体加载完成、计划内容刷新时重新计算可显示数量。

可通过看板 JS 的轻量布局测量配合 CSS 实现；优先使用
`ResizeObserver`，避免持续轮询 DOM。不要引入新的前端依赖。

## 4. 底部统计区及统计口径

统计区分为四块：

1.  选手任务执行完成率（环形进度图）。
2.  今日任务总数。
3.  训练领域分布（环形图及图例）。
4.  全天时间轴。

**统计数据只针对当前正在展示的计划，不跨计划混算。**

### 4.1 关于"个人训练完成率"的隐私边界

当前 `/training/board/` 使用
`login_not_required`，任何获得链接的人都可以访问。现有 ADR 0014
明确规定不公开选手个人执行进度。

因此，效果图中的"个人训练完成率"在匿名看板上应按**当前计划当天的选手任务执行汇总完成率**实现：

-   建议最终标题使用"选手任务完成率"或"选手整体完成率"。
-   统计基于当前计划当天已发布任务对应的 `TaskExecution` 记录。
-   只展示汇总百分比和汇总数量，不显示任何选手姓名、账号、个人百分比或个人状态明细。
-   不展示进度记录正文、问题描述、教练反馈、附件等内容。
-   如果没有有效任务分配记录，显示 `—` 和"暂无执行数据"，不要显示为 0%。

如果未来确实需要展示某一名选手的个人完成率，应另行设计登录后授权的个人看板或受控展示模式，不得把单人数据直接加入当前匿名公开接口。

### 4.2 完成率计算

以当前计划当天已发布任务的有效执行分配记录为统计对象：

``` text
有效分配数 = 未撤销且状态不为“已取消”的 TaskExecution 数量

已完成数 = 状态为 COMPLETED 的有效分配记录数量

完成率 = 已完成数 / 有效分配数 × 100%
```

规则：

-   `revoked_at` 非空的记录排除。
-   `status = CANCELLED` 的记录排除。
-   只有 `COMPLETED` 计入已完成数。
-   `IN_PROGRESS`、`ASSIGNED` 分别统计为进行中、未开始。
-   `PARTIALLY_COMPLETED`、`BLOCKED`、`UNFINISHED`
    仍计入有效分配数，但不能计为已完成；可合并显示为"其他状态"。
-   百分比按整数四舍五入。
-   统计范围仅限当前计划、当天、已发布任务，不纳入个人自主任务和其他日期任务。

统计查询只返回状态数量，不取出或序列化执行记录所属用户信息。使用数据库聚合完成统计，避免在
Python 中逐个读取执行记录。

### 4.3 今日任务总数

统计当前计划当天已发布的训练任务数量（每个任务只计一次）。

该指标与执行分配数不同：

-   今日任务总数：教练发布的任务定义数量。
-   有效分配数：这些任务分配给选手后形成的有效 `TaskExecution` 数量。

界面文案和数字必须区分两者，不要将"9 项任务"误认为"9 名选手任务分配"。

### 4.4 训练领域分布

-   以当前计划当天已发布任务为统计范围。
-   每个任务只归入一个统计领域，确保各领域任务数之和等于今日任务总数。
-   优先使用任务关联的主要技术领域。
-   缺少任务主要领域时，回退到时段主要领域；仍无法确定时归入"综合"或"其他"。
-   不要因为一个任务关联多个次要领域而重复计数。
-   环图和图例使用同一组统计结果；百分比合计应为
    100%（因四舍五入产生的微小误差除外）。
-   无任务时显示空状态，不绘制误导性的环图。

### 4.5 全天时间轴

-   展示早读、上午、下午、晚上四个时段及其时间。
-   与四个时段卡片使用同一份排班数据。
-   依据服务器当前时间标识已结束、进行中和未开始。
-   时间轴不得自行推算或硬编码各时段时间。

## 5. 后端数据改造

### 5.1 查询范围与授权

继续复用 `TrainingBoardPlan`
作为独立上屏授权，不新增公开开关或绕过授权的查询路径。

查询必须同时满足：

-   计划已加入大屏授权名单。
-   计划已发布。
-   排班已发布。
-   当前日期位于计划起止日期范围内。
-   排班日期为业务时区的当天。
-   任务已发布。
-   时段属于当前计划当天，且排班关系有效。

建议将复杂的计划、时段、任务及统计数据组装放入 `training/selectors.py`
的合适位置，或采用清晰命名的局部 selector；`training_board()` 只负责
HTTP 请求、日期和模板响应。

### 5.2 从"任务驱动"改为"计划/排班驱动"

当前实现从 `TrainingTask`
查询开始，只有存在符合条件的已发布任务时才会建立时段数据。

改造后应：

1.  先查询当天有效且已授权上屏的计划。
2.  获取每个计划当天的排班日及四个时段。
3.  再获取这些时段下已发布任务，并按时段分组。
4.  即使某时段没有任务，也能输出对应时段卡片及正确的空状态。
5.  为每个计划单独组装任务数、领域分布、执行统计和时间轴。
6.  保持稳定排序。

使用 `select_related()`、`prefetch_related()`、`Count()`
等方式控制查询数；不能在模板循环中触发 ORM
查询，也不能逐个任务查询执行记录。

### 5.3 建议的模板数据结构

以下仅表示数据组织方向，不要求机械照搬字段名：

``` python
{
    "id": plan.pk,
    "title": plan.title,
    "duty_coaches": [...],
    "slots": [
        {
            "period": "early",
            "label": "早读",
            "start": ...,
            "end": ...,
            "state": "completed|active|upcoming|unused",
            "domains": [...],
            "coaches": [...],
            "tasks": [...],
        },
        # morning / afternoon / evening
    ],
    "statistics": {
        "task_total": 9,
        "execution_total": 9,
        "completed": 7,
        "in_progress": 2,
        "assigned": 0,
        "other": 0,
        "completion_rate": 78,
        "domain_distribution": [...],
    },
}
```

模板只负责展示；统计口径和分组在 selector
中完成。若项目现有数据结构更合适，可以调整，但不能把统计逻辑转移到前端。

## 6. 前端实现

### 6.1 模板

重构 `training/templates/training/training_board.html`：

-   使用独立的 `tms-training-board` 根容器。
-   全屏布局，主体不出现页面级纵向滚动条。
-   头部、计划信息栏、四列时段卡片、底部统计区分层明确。
-   一个计划对应一个完整的看板页面容器。
-   使用语义化标题、列表、按钮和统计标签。
-   负责教练统一显示为"负责教练"，不添加"人"字。
-   空计划、空时段、无执行数据和刷新错误均有清晰状态。

### 6.2 样式

在 `static/css/main.css` 中增加看板专属样式，避免污染其他页面：

-   深蓝/藏青背景，青蓝色作为主强调色，绿色只用于完成状态。
-   卡片采用细边框、适度渐变和柔和阴影；当前时段高亮但不能过度发光。
-   统计区采用紧凑横向分区。
-   环形统计图优先使用 CSS `conic-gradient` 或 SVG；不新增
    Chart.js、ECharts 等依赖。
-   图标使用项目现有 Iconify Tailwind 4 插件和明确的图标类名。
-   使用 `clamp()`、网格布局和媒体查询控制字号、间距及卡片尺寸。
-   只在看板根容器内设置深色主题，不修改全站主题偏好。

不要直接修改 `static/css/output.css`；样式源码修改后执行
`npm run build:css` 重新生成。

### 6.3 分辨率适配

重点验证：

-   **1920×1080：** 完整展示所有信息，作为主设计尺寸。
-   **1366×768：**
    四时段仍尽量横向一屏展示，压缩装饰、间距和次要统计文字，不牺牲任务标题可读性。
-   **1280×720：**
    使用更紧凑的排版；必要时调整统计区布局，但不允许出现任务区域滚动条。
-   **更窄屏幕：** 可降为两列布局，不应强行把四列挤到无法阅读。

不以缩小所有字体作为适配手段；优先压缩装饰、内边距和次要信息。

## 7. JavaScript 改造

重构 `static/js/training-board.js`，保留原生 ES Module，不为只读看板引入
Alpine 状态层或新的轮播库。

主要职责：

1.  初始化当前计划及轮播控制。
2.  15 秒自动切换计划。
3.  上一份、下一份、暂停/继续。
4.  单计划时隐藏轮播控制。
5.  60 秒向现有公开 URL 请求最新局部 HTML，继续使用 `cache: no-store`。
6.  刷新时尽量保持当前 `data-plan-id`；计划已不存在时回到有效计划。
7.  刷新成功后重新计算任务列表可见数量和当前计划页码。
8.  监听窗口尺寸变化和任务容器尺寸变化，重新计算任务列表溢出。
9.  尊重 `prefers-reduced-motion`，后台标签页暂停自动轮播。
10. 请求失败时沿用 ADR 0014
    的安全处理：清除已展示的公开任务内容、显示刷新错误状态并继续重试。

当前脚本的分页逻辑会把一个计划拆分成多页，应删除这种"按内容高度切割计划"的行为，改为**一份计划就是一页**。时段内的任务溢出由卡片省略机制处理。

当前 `refreshAtMidnight()` 对 UTC+8 的偏移量有硬编码。项目默认业务时区为
`Asia/Shanghai`，但无需在浏览器端重复维护固定偏移量；60
秒刷新已经足以在日期变化后更新页面，可移除重复的午夜定时逻辑。

## 9. 测试与验收

### 9.1 Django 测试

在 `training/test_board.py` 增加或调整测试，至少覆盖：

-   匿名用户仍可访问大屏。
-   未授权上屏的计划不显示。
-   撤回发布或移出大屏后，下一次请求不再显示。
-   多份计划分别输出独立的四时段和统计数据。
-   计划轮播数据顺序稳定。
-   某时段无任务时仍保留时段卡片。
-   草稿、取消任务、未发布排班不进入统计。
-   任务数按任务定义计数，不与选手分配数混淆。
-   执行完成率只把 `COMPLETED` 计入完成数。
-   已撤销、已取消执行记录不进入分母。
-   部分完成、受阻、未完成等状态不能被误算为完成。
-   无有效执行记录时显示无数据状态，而不是 0%。
-   多名选手的执行记录只输出聚合数量，不输出姓名、账号、个人进度或反馈。
-   原有测试继续保证任务正文、附件、选手信息和详情链接不泄露。

## 10. 明确不做的事情

-   不新增独立大屏 APP 或新的上屏授权模型。
-   不改变训练计划、排班、任务发布和执行状态的业务规则。
-   不在匿名页面展示单个选手的完成率、姓名、账号、进度正文或教练反馈。
-   不新增图表库、轮播库或其他前端依赖。
-   不让一个计划因内容过多而被拆成多个轮播页面。
-   不用滚动条展示超出卡片容量的任务。
-   不修改全站主题、公共导航或其他页面样式。
-   不在浏览器端直接控制显示器电源、亮度或操作系统屏保；显示器节能交由操作系统和设备设置负责。

## 11. 完成标准

完成后，`/training/board/` 应达到已确认设计图的整体观感和信息层级：

-   一屏展示一份计划。
-   四个训练时段横向排列。
-   多计划按 15 秒轮播。
-   多任务按卡片容量显示，超出部分以省略提示表达。
-   底部展示准确的计划级匿名统计和全天时间轴。
-   1920×1080 与 1366×768 下均有良好可读性。
-   不破坏现有上屏授权、发布状态、匿名访问和隐私边界。
-   相关 Django 测试、前端测试和 CSS 构建通过。

**Codex 执行原则：** 先阅读当前代码和相关 ADR，确认与本 Plan
的差异；按最小必要范围实施。若发现模型字段、状态含义或授权规则与 Plan
冲突，先报告具体差异，不得自行改变训练业务规则。
