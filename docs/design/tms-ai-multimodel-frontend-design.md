# **TMS AI 多提供商管理界面设计方案**

**设计基线：V1.2**

这次我们不重新设计 AI 系统架构，而是在已经确认的 V1.2 架构基础上，把前端管理界面落实到可以交给 Codex 实施的程度。

我建议继续沿用目前的三个管理入口，不要因为后端改名为 `ai`，就把前端管理功能全部重新组织。

三个入口分别是：

1. 我的 AI 模型：用户管理自己的模型连接和模型配置。
2. AI 模型提供商：管理员维护提供商预设、默认 API 地址和模型目录。
3. 共享 AI 模型管理：管理员管理用户共享出来的模型及其使用范围。

这里有一个核心设计原则：

**用户面对的是模型连接和模型，而不是 LiteLLM 的技术概念。**

LiteLLM、Provider Adapter、模型路由等实现细节全部隐藏在后端。前端使用统一的业务语言，让用户无论接入 DeepSeek、OpenAI、通义千问，还是自定义 API，都使用尽可能一致的操作方式。

## **三、表单字段与数据规则**

下面是建议最终确定的字段清单。

### **1. 基本信息**

| 字段    | 类型        | 必填 | 规则        |
| ----- | --------- | -- | --------- |
| 模型名称  | TextInput | 是  | 1–100 字符  |
| 模型提供商 | Select    | 是  | 预设提供商或自定义 |
| 接入协议  | Select    | 是  | 根据提供商确定   |
| 备注    | Textarea  | 否  | 用户自己的说明   |

这里有一个重要区别：

- 提供商（Provider）：DeepSeek、OpenAI、阿里云等。
- 协议（Protocol）：OpenAI Compatible、Anthropic 等。
- 模型 ID（Model ID）：deepseek-chat、gpt-4.1 等。

三者不能混为一谈。

例如，一个自定义服务商可能使用 OpenAI Compatible 协议，但它并不是 OpenAI 提供商。

### **2. API 连接配置**

| 字段           | 类型            | 必填   | 规则                 |
| ------------ | ------------- | ---- | ------------------ |
| API Base URL | URLInput      | 是    | 自动填充，可覆盖           |
| API Key      | PasswordInput | 新建必填 | 加密保存               |
| API Key 预览   | 只读            | 编辑显示 | 例如 `sk-••••••1234` |
| 自定义请求参数      | 高级配置          | 否    | 第一版暂不开放任意 Header   |

特别需要注意 API Key 的编辑交互。

### **3. 模型配置**

| 字段    | 类型                 | 必填   | 说明                |
| ----- | ------------------ | ---- | ----------------- |
| 模型 ID | Select / TextInput | 是    | 支持目录选择和手动输入       |
| 模型能力  | 标签/选择器             | 否    | 文本、视觉、推理、工具调用等    |
| 能力来源  | 只读标记               | 否    | 提供商目录、人工覆盖        |
| 思考模式  | Switch             | 条件必填 | 仅支持对应能力的模型        |
| 思考强度  | Select             | 条件必填 | 低、高、最高，按适配器支持情况显示 |

模型 ID 的选择方式值得专门设计。

**预设提供商：**

- 默认展示推荐模型。
- 可以搜索模型目录。
- 允许手动输入模型 ID。
- 手动输入后显示“自定义模型 ID”标记。

**自定义提供商：**

- 不显示预设模型目录。
- 直接填写模型 ID。
- 允许填写用户熟悉的模型名称。

这里不应该强制要求用户从 TMS 内置模型列表中选择，因为新模型可能先于 TMS 的目录更新而发布。

### **4. 默认与共享设置**

建议把它们放在表单最后一个独立区块，不要与 API 连接参数混在一起。

| 字段       | 类型     | 规则                   |
| -------- | ------ | -------------------- |
| 设为个人默认模型 | Switch | 验证成功后才能生效            |
| 开启共享     | Switch | 验证成功后才能生效            |
| 共享范围     | Radio  | 全部有使用权限的用户 / 指定用户或角色 |
| 指定用户     | 多选     | 共享范围为指定时显示           |
| 指定角色     | 多选     | 共享范围为指定时显示           |

保留现有的用户权限模型：

- `manage_own_aimodel`：管理自己的模型。
- `use_shared_aimodel`：使用共享模型。

模型所有者可以管理自己的模型，但不能通过共享设置绕过使用者的权限。

测试时建议采用明确的状态：

| 状态    | 含义               |
| ----- | ---------------- |
| 待验证   | 尚未测试             |
| 正在测试  | 测试请求进行中          |
| 已验证   | 最近一次测试成功，当前配置未变化 |
| 验证失败  | 最近一次测试失败         |
| 配置已变更 | 验证成功后修改了连接配置     |

这里特别强调：验证状态应与配置版本绑定。

例如：

- 修改 API Key：验证失效。
- 修改 Base URL：验证失效。
- 修改模型 ID：验证失效。
- 修改影响 API 请求的高级参数：根据实际参数是否影响连通性决定是否失效。
- 修改显示名称：不需要失效。
- 修改共享范围：不需要失效。

测试成功后才能设为默认或开启共享。

### **2. 连接测试结果**

测试结果不要只显示“成功”或“失败”。

建议包含：

- 连接结果。
- HTTP 状态或分类后的错误类型。
- 模型响应是否正常。
- 请求耗时。
- 测试时间。
- 安全处理后的错误信息。

绝不能将 API Key、Authorization Header 或完整敏感请求内容写入前端错误提示和日志。

对于网络错误、401、429、余额不足、模型不存在等情况，应尽可能给出用户能理解的中文提示。

## **六、模型目录管理界面**

管理员的“AI 模型提供商”页面，应该与用户的“我的 AI 模型”分开。

它不是管理用户的 API Key，而是管理 TMS 能识别和推荐哪些模型。

建议采用两级界面。

### **1. 提供商列表**

| 字段           | 说明                  |
| ------------ | ------------------- |
| 提供商名称        | DeepSeek、OpenAI 等   |
| Provider Key | 稳定标识                |
| API 协议       | OpenAI Compatible 等 |
| 默认 API 地址    | 系统默认地址              |
| 模型数量         | 当前目录模型数量            |
| 状态           | 启用、停用               |
| 操作           | 编辑、管理模型             |

### **2. 提供商详情**

进入 DeepSeek 后，展示：

- 提供商基本信息。
- 默认 API Base URL。
- 默认协议。
- 推荐模型目录。
- 默认模型。
- 模型能力。
- 模型是否推荐。
- 是否允许手动输入模型 ID。

模型目录建议包含以下字段：

| 字段     | 说明          |
| ------ | ----------- |
| 模型 ID  | 实际 API 调用标识 |
| 显示名称   | 目录展示名称      |
| 模型类型   | 通用、推理、多模态等  |
| 能力标签   | 文本、视觉、推理等   |

这里有一个重要原则：

**模型目录是推荐和辅助选择机制，不是用户接入模型的限制机制。**

用户可以使用目录以外的模型 ID。

同时，模型目录中的能力信息不能直接当成模型真实能力的验证结果，应明确区分官方资料、管理员配置和用户自定义。

## **七、前端交互规则汇总**

我建议将下面这些规则作为正式的前端设计规范。

| 场景         | 交互规则            |
| ---------- | --------------- |
| 选择提供商      | 自动填充协议、默认地址     |
| 切换提供商      | 提醒可能覆盖当前连接参数    |
| 修改 API 地址  | 允许覆盖默认值         |
| 输入 API Key | 密码遮罩            |
| 编辑 API Key | 留空保留，输入新值替换     |
| 选择模型       | 目录选择或手动输入       |
| 选择模型能力     | 按目录元数据动态展示      |
| 思考模式       | 仅支持的模型显示        |
| 保存模型       | 只保存，不自动测试       |
| 连接测试       | 在模型详情页主动执行      |
| 测试失败       | 不允许设为默认或共享      |
| 修改连接参数     | 使原验证状态失效        |
| 设置默认模型     | 每个用户只能有一个个人默认模型 |
| 开启共享       | 必须通过验证          |
| 删除模型       | 检查默认设置、引用及共享状态  |

例如用户已经填写：

- 提供商：DeepSeek
- API 地址：DeepSeek 官方地址
- API Key：已填写
- 模型 ID：deepseek-chat

这时切换到 OpenAI，不能静默地覆盖所有字段。

建议显示确认提示：

**切换模型提供商？**\
切换提供商可能改变当前 API 协议、默认 API 地址和模型目录。

已填写的 API Key 不会自动用于新提供商。

取消确认切换

另外，如果用户只是修改了提供商默认地址，而没有改变实际连接目标，也不应无条件丢失已有配置。

## **八、几个我认为值得进一步明确的设计细节**

### **1. 不要把连接配置与模型能力混为一谈**

未来可能出现这样的情况：

一个企业内部 AI 网关，提供了多个模型：

- 模型 A：文本生成。
- 模型 B：文本生成、推理。
- 模型 C：文本生成、视觉理解。

它们可以使用同一个 API Base URL 和 API Key，但具有不同的模型 ID 和能力。

因此从长期数据模型来看，最好区分：

- Provider：提供商身份。
- Connection：API 接入连接及认证信息。
- Model：具体模型及能力。
- Model Preference：默认模型选择。

不过，结合目前已经确定的 V1.2 设计，我不建议为了追求这种抽象，马上引入复杂的连接实体和多模型共享凭据体系。

第一版继续以现有 AIModel 为用户管理的核心对象，模型级保存连接参数。后续如果确实需要一个连接下挂多个模型，再独立演进。

### **2. 默认模型应该考虑业务场景**

目前已有个人默认模型的概念。

未来 TMS 可能同时存在：

- 教练训练日志生成。
- 选手训练日志生成。
- 训练数据分析。
- AI 助手对话。
- 考核结果分析。

这些场景不一定适合使用同一个模型。

因此建议在现有个人默认模型基础上，为后续的业务默认模型预留设计空间。

但第一版不需要在新增模型表单中增加大量业务场景选择项。先把个人默认模型做好。

### **3. 不要让前端承担模型协议适配工作**

这是整个系统最重要的架构边界。

前端只负责：

- 选择提供商。
- 选择协议。
- 填写连接信息。
- 选择模型。
- 配置模型参数。
- 管理权限和共享。
- 展示连接状态。

后端 `ai` 负责：

- 提供商注册表。
- 模型目录。
- LiteLLM Core 调用。
- 专属 Provider Adapter。
- 参数转换。
- 连接测试。
- 统一错误处理。

不能因为某个模型支持特殊参数，就在模板里增加针对该提供商的硬编码判断。

## **十、最终视觉设计与技术实现建议**

结合 TMS 当前使用的 Django、django-htmx、Tailwind CSS 4、DaisyUI 5、Alpine.js 和 Iconify，我建议：

| 界面元素  | 实现建议                    |
| ----- | ----------------------- |
| 模型列表  | 复用 `django-tables2`     |
| 提供商选择 | DaisyUI 下拉/弹出选择面板       |
| 模型选择  | Alpine.js 搜索式选择器        |
| 动态表单  | Django Form + HTMX 局部更新 |
| 高级设置  | DaisyUI Collapse        |
| 开关    | DaisyUI Toggle          |
| 密钥输入  | 原生 Password Input       |
| 测试状态  | Badge + HTMX 状态更新       |
| 错误提示  | TMS 统一 Toast            |
| 删除确认  | 统一确认弹窗                  |

不要为了这套界面引入新的前端框架，也不需要把所有交互都改成 HTMX。局部动态交互可以合理使用 Alpine.js，服务端校验仍以 Django Form 为准。

## **我的最终意见**

我认为这套设计最值得坚持的有四点：

1. **统一表单**：不为 DeepSeek、OpenAI、其他提供商分别开发一套完全不同的新增模型页面。
2. **动态能力**：根据 Provider 和 Model 的元数据动态显示字段，而不是在模板中写死提供商判断。
3. **连接与模型分离的设计方向**：保留未来一个连接支持多个模型的演进空间，但第一版不增加不必要的数据库复杂度。
4. **业务操作优先**：用户不需要理解 LiteLLM、Adapter、Router 等技术实现，只需要能够顺利接入和使用模型。

我建议把本次方案作为 V1.2 的前端正式设计基线。下一步可以将它整理成一份独立的 Codex 前端实施 Plan，与之前的 AI 多模型后端及 APP 迁移 Plan 配套执行。
