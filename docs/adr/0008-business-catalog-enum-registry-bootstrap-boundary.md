# ADR 0008：业务目录、Enum、Registry 与 Bootstrap 边界

- 状态：已接受
- 日期：2026-08-24

## 背景

TMS 曾把部分可由管理员维护的业务分类保存为 `TextChoices`，同时由生产 Fixture 或普通读取路径补齐默认数据。这会把运营配置与程序语义混在一起，也可能在读取、启动或升级时意外写库并覆盖管理员预期。另一些选项背后实际依赖解析器、模板、样式、权限或状态流转实现，不能仅靠数据库新增一行就获得能力。

## 决策

1. 管理员可以新增、改名、排序、启停且程序无需新增处理逻辑的值，使用各业务 APP 自有的具体 Model 目录。目录使用稳定 `code` 作为机器身份；已有引用后锁定代码，展示名称与启用状态可维护，历史外键通常使用 `PROTECT`。
2. 生命周期、审核状态、协议值和结构关系等程序必须理解的有限值域继续使用 Enum / `TextChoices`。新增值必须连同状态流转、校验、查询、统计和界面行为一起评审。
3. 解析器、主题、权限包等依赖代码实现或受版本控制资源的能力使用代码 Registry 或静态配置。数据库只能保存已注册实现的启用、默认、显示名称和排序，不能创造不存在的实现。
4. `bootstrap_tms` 是生产和新环境默认业务数据的统一显式初始化入口。它按稳定代码幂等创建缺失项，不覆盖管理员修改，并在一个外层事务中执行；名称或 Registry 键冲突时整体失败并回滚。
5. Request、selector、普通读取 service、`AppConfig.ready()` 和 signal 不得隐式 Bootstrap。正常部署不反复执行 Bootstrap；历史数据迁移继续保存为迁移快照，Fixture 仅用于测试、演示或显式数据交换。
6. 仓库没有权威默认值的可配置目录保持为空，不因“可配置”而由实现者自行发明出厂数据。

## 后果

管理员可以在不改代码的情况下维护真正的业务目录，停用项不会进入新业务但仍可解释历史记录。程序语义和实现能力仍受代码评审与版本发布约束。新环境在迁移后需要显式执行一次 `uv run manage.py bootstrap_tms`；后续如需补充强制基础数据，应使用明确的数据迁移或发布说明，而不是依赖启动时同步或生产 Fixture。
